# latent-cot-motion 项目审核报告

## 1. 审查背景与范围
- 项目路径：`latent-cot-motion`
- 审查日期：2026-02-23
- 审查目标：定位训练、推理、评估链路中的逻辑问题与工程稳定性问题，并给出可落地修复优先级。
- 审查对象：`train.py`、`dataset.py`、`coconut_motion.py`、`inference.py`、`evaluate.py`、`build_data.py`、`run.sh`、`configs/t2m_coconut.yaml`、`GUIDE.md` 及近期日志。
- 环境说明：训练脚本使用 `motionR1` 环境（`python`，见 `run.sh:11`）；分布式启动使用 `torchrun`（见 `run.sh:12`）。

## 2. 结论概览
- 结论：项目主体可运行，但存在会影响实验正确性与稳定性的高优先级问题，需要先修再继续大规模训练。
- 问题分级统计：`P0` 2项，`P1` 3项，`P2` 3项，`P3` 2项。
- 训练运行信号：日志存在端口冲突、子进程 `SIGKILL`、tokenizer fork 警告，以及较低生成指标（`Gen token_acc: 0.0009`，见 `logs/train_20260223_164429.log:2486`）。
- Public APIs / Interfaces / Types：本报告仅审查，不修改接口或数据格式；`None`。

## 3. 高优先级问题（P0/P1）

1. `P0`：`cot` 模式会被随机 stage 采样污染，导致“纯 CoT”不纯。
现象：训练阶段将 `cot/no_cot` 统一设为 `scheduled_stage=0`，但数据构造仍会依据 `uniform_prob` 随机改写 stage。  
代码证据：`train.py:582`、`dataset.py:151`、`dataset.py:170`。  
影响：`cot=true` 时仍可能注入 latent token，训练目标与实验设定不一致。  
建议修复方向：在数据集构造中仅对 `coconut` 模式启用 `uniform_prob`；对 `cot/no_cot` 显式禁用随机 stage。

2. `P0`：推理/评估输入构造与训练模式不一致。
现象：推理和评估默认固定注入最大 latent 数，未按 `cot/no_cot/coconut` 切换输入模板。  
代码证据：`inference.py:123`、`evaluate.py:104`、`train.py:846`。  
影响：模式实验对比失真，离线评估结果可能无法真实反映对应训练策略。  
建议修复方向：抽象统一的“模式到输入模板”函数，训练验证、`evaluate.py`、`inference.py` 共用。

3. `P1`：分布式启动脚本存在稳定性风险（固定端口 + 管道错误传播不足）。
现象：`run.sh` 固定 `master_port=29501`，日志已出现端口占用导致启动失败。  
代码证据：`run.sh:49`；日志 `logs/train_20260223_161026.log:16`、`logs/train_20260223_161026.log:48`。  
影响：多任务并行或残留进程场景下，训练会直接失败。  
建议修复方向：支持 `MASTER_PORT` 外部注入或自动探测空闲端口；脚本启用 `set -euo pipefail`。

4. `P1`：训练与推理/评估 checkpoint 形态兼容性不足。
现象：训练支持 FSDP 保存 `model_state.pt`，但推理/评估脚本仅按 `from_pretrained` 路径加载。  
代码证据：`train.py:751`、`train.py:766`、`inference.py:93`、`evaluate.py:67`。  
影响：切换 FSDP 后，离线评估与推理脚本可能无法直接加载权重。  
建议修复方向：抽取统一 checkpoint 加载工具，同时兼容 HF 目录与 FSDP `model_state.pt`。

5. `P1`：训练稳定性出现进程被系统杀死（`SIGKILL`）的历史记录。
现象：分布式子进程在 epoch 中途被 kill。  
日志证据：`logs/train_20260223_161433.log:119`、`logs/train_20260223_161433.log:128`。  
影响：长跑训练中断，可能造成 checkpoint 间隔过大与资源浪费。  
建议修复方向：优先减小瞬时压力（batch/worker/缓存策略），并增加异常退出时的诊断日志。

## 4. 中低优先级问题（P2/P3）

1. `P2`：文档与实现存在漂移。
现象：`GUIDE.md` 提供 `--parquet-path` 参数，但实际脚本未定义；部分超参示例与当前配置不一致。  
证据：`GUIDE.md:62`、`GUIDE.md:75`、`GUIDE.md:159`、`build_data.py:303`、`configs/t2m_coconut.yaml:23`。  
影响：按文档复现实验会踩坑，增加排障成本。  
建议：同步文档到当前实现，移除失效参数描述。

2. `P2`：空数据集场景下错误提示不友好。
现象：`get_dataset` 直接访问 `data[0]`，空数据时会抛底层异常。  
证据：`dataset.py:76`、`dataset.py:79`。  
影响：数据构建异常时定位困难。  
建议：添加显式空数据校验并报出路径与建议。

3. `P2`：指标语义注释与实现口径不完全一致。
现象：注释描述“按较短长度计算”，实现采用 `gt_len` 归一化。  
证据：`utils.py:47`、`utils.py:62`。  
影响：指标解释容易歧义，跨实验对比口径不清晰。  
建议：保留公式或调整公式二选一，但注释必须与实现一致。

4. `P3`：硬编码绝对路径影响可移植性。
现象：多个脚本直接写死 `machine-specific workspace` 路径。  
证据：`inference.py:40`、`evaluate.py:41`、`build_data.py:30`、`build_data.py:305`。  
影响：跨机器迁移与容器化部署困难。  
建议：改为配置项或环境变量。

5. `P3`：tokenizer fork 警告持续出现。
现象：日志反复提示 `tokenizers` 在 fork 后关闭并行。  
证据：`logs/train_20260223_164429.log:198`、`logs/train_20260223_164429.log:202`。  
影响：潜在性能与稳定性风险。  
建议：启动脚本设置 `TOKENIZERS_PARALLELISM=false`，并检查 tokenization 与 DataLoader 多进程顺序。

## 6. 修复计划与里程碑
1. 里程碑 M1（正确性优先）
统一 `cot/no_cot/coconut` 的 stage 与输入构造逻辑，修复训练/评估/推理不一致问题。

2. 里程碑 M2（稳定性优先）
改造 `run.sh` 端口与错误传播机制，加入 tokenizer 并行环境变量，补齐异常场景日志。

3. 里程碑 M3（兼容性优先）
实现统一 checkpoint loader，覆盖 HF 与 FSDP 两种保存形态。

4. 里程碑 M4（可维护性优先）
修正文档漂移、增加空数据友好报错、统一指标注释口径，完善回归测试。

## 7. 回归验证用例
1. 模式一致性：`cot=true` 且 `uniform_prob>0` 时，输入中不得出现 latent token。
2. `no_cot` 回归：训练、验证、推理输入均不含 latent 区域。
3. `coconut` 回归：默认配置可完整跑通至少 1 epoch，并产出 checkpoint。
4. 启动稳健性：占用默认端口后，脚本可自动换端口或明确失败并返回非 0。
5. 权重兼容性：同一 checkpoint 可被训练恢复、`evaluate.py`、`inference.py` 共同加载。
6. 空数据场景：空 JSON 输入时给出明确错误信息，而非底层索引异常。
7. 指标口径：`compute_motion_accuracy` 注释与实现一致，并有测试锁定。
